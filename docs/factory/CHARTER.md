# Factory charter — Studio Baton

**ไฟล์นี้คือ "ดุลยพินิจของมนุษย์" ที่อยู่เหนือ AI ทุกตัว** — ทุก skill ต้องอ่านก่อนลงมือ
เจ้าของเป็นคนเดียวที่แก้ไฟล์นี้ได้ AI แก้เองไม่ได้ เว้นแต่เจ้าของสั่งชัดใน session นั้นๆ
(อนุมัติเนื้อหา 2026-08-23 · ติดตามลง origin/main ผ่าน FQ-40 วันที่ 2026-08-26)

```
CHARTER_STATUS: ready
```

## 1. Tier — ระดับอิสระของ AI

`revival` กว้างสุด · `greenfield` กว้าง · `oss` ปานกลาง (AI จัดลำดับ มนุษย์ merge ทุกครั้ง) ·
`client-production` แคบสุด

```
TIER: greenfield
```

**เหตุผล:** ปล่อยสาธารณะแต่ใช้งานเจ้าของคนเดียว ทว่ามีข้อมูลลูกค้าจริงเบื้องหลัง adapter — เผื่อความระวังไว้เหนือ greenfield ปกติ

## 2. Load-bearing paths — โซนห้าม AI แตะเองเด็ดขาด

ไฟล์ที่ AI **ห้ามแก้** นอกจากมนุษย์สั่งใน session นั้นๆ — งานไปเจอโซนนี้ = หยุด ส่งคืนคน

```
LOAD_BEARING:
  - "src/baton/exits.py"
  - "src/baton/errors.py"
  - "src/baton/contracts/**"
  - "src/baton/adapters/chat/**"
  - "pyproject.toml"
  - "uv.lock"
  - ".github/workflows/**"
  - ".factory/**"
  - ".claude/**"
  - ".agents/**"
  - ".codex/**"
  - "AGENTS.md"
  - "docs/factory/CHARTER.md"
  - "docs/factory/CONTRACT.md"
  - "review/**"
  - "tools/check_leaks.py"
```

เหตุผลโดยสรุป: exit-code/errors คือสัญญาที่ script กลางคืนพึ่งพา · `contracts/**` คือเทสต์คู่
fake-vs-จริง (AI แก้เอง = หลักฐานเชื่อไม่ได้) · `adapters/chat/**` ส่งข้อความถึงผู้ปกครองจริง ·
`pyproject.toml`/`uv.lock` คือนโยบาย dependency ที่ตั้งใจให้เล็กสุด · `review/**` คือหลักฐาน
ตรวจสอบของมนุษย์ · `tools/check_leaks.py` ตัวตรวจต้องไม่ถูกตัวตรวจแก้ · ที่เหลือคือกติกาของ
factory เอง (AI ที่แก้กฎของตัวเองได้ = ไม่มีกฎเหลือ) — นอกกฎเหล่านี้แก้ได้แบบมีเทสต์คุม

## 3. กติกาไฟล์เทสต์

```
TESTS_ARE_LOAD_BEARING: true
```

AI ห้ามแก้ไฟล์เทสต์ที่มีอยู่แล้ว (เพิ่มไฟล์ใหม่ได้) — ประสบการณ์จริงคือ AI มักแก้ assertion
ให้ตรงกับพฤติกรรมที่พังแล้วรายงานว่า "เขียว" ซึ่งเป็นหลักฐานปลอม

## 4. งานที่ทำได้ / ต้องคุย / ห้ามทำ

```
AUTOMATABLE:
  - แก้บั๊กระดับ M ใน review/findings.md ที่เป็น single-file fix พร้อม failing test ใหม่
  - แก้การใช้ exit-code / error envelope ใน cli/ ให้ตรงสัญญาใน exits.py (แก้ที่ผู้เรียกใช้)
  - แก้คำอ้างใน README/docs ให้ตรงพฤติกรรมจริง
  - เพิ่มเทสต์ใหม่ให้พฤติกรรมที่ยังไม่มีเทสต์คลุม

NEEDS_SPEC:
  - ทุกรายการใน findings.md ที่สถานะ "ต้องถามเจ้าของ"
  - การเปลี่ยนความหมายของ exit-code ที่มีผลต่อผู้เรียกใช้เดิม
  - งานที่แตะมากกว่า 5 ไฟล์
  - ทุกงานที่แตะ LOAD_BEARING
  - การตัดสินใจเรื่อง parity กับ legacy (รายการ P)

NEVER_AUTOMATE:
  - Merge
  - เตรียม release / ปั๊มเลขเวอร์ชัน / แตะ release workflow
  - อัปเกรด dependency
  - ทิศทางสถาปัตยกรรม
  - ส่งข้อความจริงถึงมนุษย์ทุกชนิด (LINE/Telegram/webhook) — เทสต์ต้องใช้ fake เท่านั้น
  - แตะข้อมูลผู้เรียนจริงใน profile ที่ใช้งานจริง
  - ทุกอย่างที่ charter นี้ไม่ได้กล่าวถึง (default deny)
```

บรรทัดสุดท้ายสำคัญที่สุด: **ความเงียบ = หยุดถาม ไม่ใช่ใช้ดุลยพินิจเอง**

## 5. นิยาม "เสร็จ"

```
DONE:
  - gates รายงาน FACTORY_GATES status=GREEN ตามระดับที่งานกำหนด — จนกว่า #42 จะติดตามตัวรัน
    gates ลง repo คำตัดสินคือ CI แปด check บน GitHub ตาม contract
  - มีเทสต์ใหม่ที่แดงก่อนแก้และเขียวหลังแก้ (slice ที่ไม่แตะโค้ดผลิต: ข้อนี้ไม่ใช้)
  - ไม่มีไฟล์เทสต์เดิมถูกแก้
  - diff ทำเฉพาะสิ่งที่ issue บอกไว้เท่านั้น
  - คนอ่าน PR เข้าใจได้โดยไม่ต้องถามว่า "ทำไมปลอดภัย"
```

## 6. ระดับ gates ตามชนิดงาน

```
GATES:
  default: full
  load_bearing: deep
  docs_only: fast
```

หมายเหตุ: ระดับ `deep` ต้องการ `pip-audit` ซึ่งยังไม่พร้อมในสภาพแวดล้อม — จนกว่า slice F3
(#42) จะจัดให้ งาน load-bearing จะโดนบล็อกแบบ fail-closed ซึ่งถูกต้องตามดีไซน์

## 7. เงื่อนไขหยุด

```
STOP_IF:
  - Gates แดงติดกัน 2 ครั้งในงานเดียวกัน
  - งานบังคับให้แตะ LOAD_BEARING โดยไม่ได้รับอนุมัติใน session นั้น
  - diff เกิน 400 บรรทัด
  - issue ยังกำกวมหลังถามเจ้าของ 1 ครั้งแล้ว
  - มีงานมากกว่า 3 รายการรอมนุษย์ review
```

เงื่อนไขสุดท้ายคือวาล์วระบายแรงดัน: เมื่อคิว review เต็ม **หยุดผลิต** — คอขวดคือความสนใจ
ของเจ้าของ ไม่ใช่จำนวน AI ที่รันได้พร้อมกัน
